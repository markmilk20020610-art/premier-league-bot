# 仓库体积与 state.json 膨胀：实测数据与处置

> 记录时间：2026-10-31 · 数据来自真实仓库 `markmilk20020610-art/premier-league-bot`

## 1. 问题是什么

`state.json` 被 git 跟踪（这是设计需要：Actions 每轮要把状态回写进仓库，
否则下一轮就丢了「已推送过哪些新闻」）。它每轮扫描都会变，因此**每轮都会产生一次提交**。

按 cron-job.org 每 10 分钟一次计算，最坏情况是 **144 次提交/天、约 5.2 万次/年**。

## 2. 实测结论：没有想象中严重

最初的估算是「每次提交 62KB × 144 次 = 1.3MB/天、一年 400MB+」。**这个估算错了**，
因为它假设 git 每次都完整存一份新文件。实际上 git 用 delta 压缩：

```
state.json 历史 blob 数：44
各版本压缩后占用：最大 21,334 字节（首次全量），之后迅速衰减到
                  1,543 → 33 → 29 → 24 字节
历史总占用：0.04 MB
整个 .git：645 KB（size-pack 499 KB）
```

也就是说，**后续每版的真实成本是几十字节到 1KB**，年增长约 **15 MB**，不是 400MB。

同时验证了另一个方向：`state.json` 当前 61,901 字节，其中

| 组成 | 体积 | 占比 |
|---|---|---|
| `news_pool`（84 条 × 598 字节） | 50,302 | **81%** |
| `events`（7 条） | 3,565 | 6% |
| `processed_urls`（18 条） | 2,033 | 3% |

所以「裁剪 desc 字段」没有意义——`desc` 合计只有 7,225 字符。体积主要来自
每条 8 个字段名 + 完整 URL + 两个 ISO 时间戳。

## 3. 做了什么（低成本加固，零业务风险）

| 措施 | 位置 | 作用 |
|---|---|---|
| 体积警戒线 | `scripts/watchdog.py` `MAX_STATE_KB = 250` | state.json 超 250KB 时看门狗直接报警，把慢性膨胀变成可见故障 |
| 不触发自检 | `scanner.yml` `paths-ignore: state.json` | 只回写 state 的提交不再触发 verify job（`commit_state.sh` 的 `[skip ci]` 是第一道保险，这是第二道） |
| 明确清理 | `.gitignore` | `run_telemetry.log` / `*.merge.tmp` / `.state-remote.json` 永不入库 |

没有做的事，以及为什么：**没有把 `news_pool` 拆成独立文件**。
拆分会同时改动 `bot.py` 的存取、`commit_state.sh`、`merge_state.py` 和三组测试，
而收益是把年增 15MB 降到 6MB——**收益不足以抵偿改坏状态机的风险**。

## 4. 什么情况下才需要升级方案

出现下列任一情况，再考虑拆分（届时有明确数据支撑，不是猜）：

1. `.git` 体积 > 100 MB；
2. `state.json` 常态 > 250 KB（看门狗会先报警）；
3. `git clone` 明显变慢（> 10 秒）；
4. 提交数 > 10 万条导致 `git log` 卡顿。

升级路径（按代价从低到高）：

1. **降低回写频率**：`commit_state.sh` 比较新 state 与 HEAD，若只有 `news_pool`
   和 `last_scan_at` 变化且距上次提交 < 20 分钟则跳过（心跳 3 小时阈值仍有充足余量）。
2. **拆池**：`news_pool` 移到 `pool.json`，只在早报运行或池子新增 ≥ N 条时提交。
3. **换存储**：state 改放 Actions Cache / 外部 KV，仓库只留代码。代价是引入新依赖，
   与「不引入付费服务」的约束冲突，属于最后手段。

## 5. 顺带记录：为什么不用紧凑 JSON

`json.dumps(..., separators=(',', ':'))` 只能把 61,901 字节压到 55,358（**省 11%**），
因为体积大头是中文文本和 URL 而不是缩进。为了 11% 牺牲 diff 可读性不划算，故未采用。
