# 调度单点故障方案 + 对手发布时间采集

> 2026-10-31
> 回应两个问题：① cron-job.org 挂了怎么办；② 授权采集对手发布时间后的落地

---

## 一、问题不在「cron-job.org 会不会挂」，而在「挂了没人知道」

现有链路：

```
cron-job.org ──dispatch──> GitHub Actions ──> bot.py ──> Telegram
```

`cron-job.org` 是唯一触发器。但真正致命的不是单点，而是**看门狗和被监控对象共用同一条链路**：

`scripts/watchdog.py` 负责发现「扫描停了」，可它自己是靠 GitHub 的 `schedule` 触发的。
而 GitHub `schedule` 在本仓库实测 3 天只触发 7 次、早报迟到 207 分钟。
**它连自己都保证不了，更不可能保证能发现别人的故障。**

这就是为什么之前「早报 09:28 才到」这件事，是用户先发现的，不是系统发现的。

### 顺带修掉一个失效的阈值

`watchdog.py` 原来的 `MAX_SCAN_AGE_HOURS = 3`——意思是「扫描停了 3 小时才报警」。
按 5 分钟一轮算，那是连续丢了 36 轮。已改为 **30 分钟**（可用
`WATCHDOG_MAX_SCAN_AGE_MINUTES` 覆盖），连续丢 6 轮就暴露。

## 二、方案：三层冗余 + 按心跳缺口接管

| 层级 | 角色 | 频率 | 依赖 | 状态 |
|---|---|---|---|---|
| 主 | cron-job.org | 1 分钟（需你改） | cron-job.org | 已用 |
| 备 | **Cloudflare Worker**（`deploy/cloudflare-worker/`） | 1 分钟 | Cloudflare 免费档 | **代码已就绪，待你部署** |
| 兜底 | GitHub `schedule` `*/5` | 5 分钟（极不规律） | GitHub | 已启用 |
| 观察 | Worker 兼做外部看门狗 | 1 分钟 | Cloudflare | 同上 |

### 关键设计：备份不是「同时开两份」，而是「按心跳缺口接管」

Worker 每分钟读一次 `state.json` 的 `last_scan_at`：

| 心跳年龄 | 动作 |
|---|---|
| < 6 分钟 | 主调度器正常，**什么都不做** |
| ≥ 6 分钟 | 主动 dispatch 一次，把流水线拉起来 |
| ≥ 20 分钟 | 额外发一条 Telegram 告警：「cron-job.org 可能挂了」 |

主调度器恢复后 Worker 自动闭嘴，不需要人工切换。

### 为什么多重触发不会重复推送

- `concurrency` 把并发 run 串行化；
- `state.json` 里 `processed_urls` / `news_pool` / `events` 三层去重，第二轮发现没新内容就 0 推送退出。

这是项目本来就有的性质，不是本方案新增的假设。

### 为什么不用「每分钟都 dispatch」

那等于每轮跑两次，纯浪费。按心跳缺口判断，天然实现主备切换。

### 提供两个实现，任选其一

- `deploy/cloudflare-worker/worker.js` —— Cloudflare Worker（推荐，免费额度充足）
- `deploy/cloudflare-worker/README.md` 里的 **Google Apps Script** 版本 —— 不想注册 Cloudflare 就用它，Google 账号即可

两者都需要一个 GitHub PAT（权限只开 `Actions: write` + `Contents: read`），
部署步骤写在 README 里，含验证命令。

## 三、必须说清楚的三件事

1. **Worker 代码没有在真实账号上跑过。** 我没有你的 Cloudflare 账号，也没有 PAT。
   代码逻辑简单（读心跳 → 判断 → dispatch → 告警）、带只读探活接口，但
   **部署后必须按 README 的「第 3 步验证」走一遍**，确认 `age_minutes` 会随心跳更新。
2. **这套方案保证的是「单点故障不至于永久静默」**，不是「永不中断」。
   所有外部调度同时挂掉时，只剩 GitHub 兜底，而它本来就不可靠。
3. **最坏情况下的表现**：主调度器挂 → 最多 6 分钟后 Worker 接管 → 20 分钟后你收到告警。
   也就是说**最长静默 6 分钟**，而不是 3 小时。

## 四、对手发布时间采集（已实现并验证）

### 4.1 三个源全部实测可采

| 源 | 入口 | 时间精度 | 实测 |
|---|---|---|---|
| 懂球帝 | `www.dongqiudi.com/api/app/tabs/web/1.json` | 秒 | 46KB JSON，含 title/url/时间 |
| 虎扑 | `soccer.hupu.com` | 秒 | 页面内嵌 JSON，`publishTime` + `addTime` 双时间可交叉校验 |
| 直播吧 | `news.zhibo8.cc/zuqiu/` | 列表只有日期，文章页有秒 | 需补 1 次请求 |

### 4.2 第一个真实基线（今晚 Chelsea vs Man Utd，开球 12:30Z）

| 源 | 首发发布时刻 | 距开球 | 标题 |
|---|---|---|---|
| 虎扑 | **11:16:12Z** | **T-74 分钟** | 剑南春首发-切尔西vs曼联：B费领衔，帕尔默、库尼亚出战 |
| 直播吧 | 11:16:56Z | T-73 分钟 | 切尔西vs曼联首发：B费回归！帕尔默、埃斯特旺 约罗、库尼亚先发 |

两个源相差 **44 秒**。这组数字说明三件事：

1. **首发确实在 T-75 前后出现** —— §5 的「T-75 起 30 秒轮询」设计被真实数据印证；
2. 对手之间的竞争是以**秒**计的，慢一分钟就输了；
3. 我们现在有了可对照的靶子：要证明领先，就得在 11:16:12Z 之前检测到。

### 4.3 一个必须记住的限制：资讯流窗口很浅

同一批数据在 13:05Z 还能抓到上面那条，到 13:15Z（40 分钟后）就已经滚出
虎扑（20 条）和懂球帝（9 条）的第一页了。

结论：**对手发布时间无法事后回溯，只能前瞻性高频轮询捕获。**
所以采集必须和首发监控跑在同一个高频循环里，不能靠「赛后补数据」。

### 4.4 防封：补请求有上限

直播吧列表页近 1000 条，每条都要单独请求文章页才能拿到时分秒。
不加限制一次调用会打出上百个请求——被限流甚至封 IP 之后，连「我方检测时间」都拿不到。

因此 `find_lineup_mentions(max_resolve=5)` 只对最可能的 5 条补请求
（按日期贴近开球日排序），并有专门测试 `test_resolve_requests_are_capped` 守着。

### 4.5 时间戳脏数据

懂球帝的置顶文章实测出现过 `published_at = 2030-10-30`（未来时间）。
直接拿来算会得出「对手比我们早 4 年」。所有时间戳都要求落在
`[now-24h, now+10min]`，越界一律标 `suspect` 并排除出速度计算；
有 `created_at` 时退回用它。
