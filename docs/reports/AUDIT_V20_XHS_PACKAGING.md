## 零、五条硬结论

1. **A/B/C 三稿已经存在，但不是 V2.0 要的那三稿。** 现有是 `争议拆解型 / 证据核验型 / 机制解释型`（`bot.py:1237-1247`），V2.0 要的是 `冲突悬念型 / 真相拆解型 / 利益影响型`。**A、B 需要补结构，C 需要重写叙事逻辑**——现有的 C 讲「机制怎么运作」，V2.0 的 C 讲「谁受影响」，这是两回事。

2. **封面体系差距最大。** 现在只有一个自由文本 `cover_blueprint` + 一个 ≤8 字 `banner_overlay_text`（`bot.py:1289-1291`），**没有任何构图规范、没有三行标题层级、没有比例要求、没有可复制的完整提示词**。V2.0 要的五区构图 + 三层标题 + 3:4/16:9 双比例 + 无文字备用提示词，**全部为零**。

3. **有一个会直接卡死整个功能的技术上限。** `AI_MAX_TOKENS_ANALYZE = 2200`（`ai_provider.py:170`）。而 V2.0 单条新闻的完整输出实测估算 **4300–5000 字**（三稿正文 1800–2700 + 两份长提示词 1300–1600 + 9 标题 + 3 行封面标题 + 标签 + 风险提示 + 评分）。**按现有上限必然截断 → JSON 解析失败 → 整条新闻被丢弃。** 这不是「可能」，是算术。

4. **Telegram 单条 4000 字符会被撑爆。** V2.0 卡片约 4000–5500 字符，会切成 2 段。`_split_html`（`bot.py:243`）按行聚合，**如果小红书正文是单个长行，会在行内硬切、断在半句话上**。分块能力本身是有的（`test_long_message_splits_into_multiple_chunks` 已验证），但没针对这种内容测过。

5. **事实分层只做了事件级，V2.0 要的是句子级。** 现有 `evidence_status` 四值（`evidence.py:32-43`）是**程序按证据链算出来的事件级结论**，很扎实；但 V2.0 的 `FACT / REPORTED / INFERENCE / SPECULATION` 需要在同一篇稿子里逐句区分。**现有架构没有这个能力**，`INFERENCE` 和 `SPECULATION` 完全没有对应物。

### 5.2 现在的 `image_prompt` 长什么样（实测样例）

```

```

**这就是全部。** 没有构图、没有文字、没有比例、没有光影描述。V2.0 要的是 700–1000 字的完整中文提示词。**这不是「优化」，是「从零建」**。

### 5.3 一个必须先确认的技术问题

V2.0 §二.4 自己写了：

> 「如果豆包无法稳定生成准确中文文字，则必须额外输出无文字背景图提示词，并给出后期文字叠加方案」

**这个「如果」需要你确认。** 据我所知，豆包（以及绝大多数文生图模型）对中文长句的渲染**极不稳定**，多行标题几乎必出错字或乱码。所以我的建议是：

- **默认走「无文字背景图 + 后期叠加」路线**，而不是赌模型能写对 3 行中文。
- 提示词默认输出两份：`doubao_bg_prompt`（无文字，主用）+ `doubao_full_prompt`（带文字，备用）。
- 同时输出叠加方案：每行文字、位置（九宫格坐标）、字号层级、颜色、描边宽度。

这一点需要你拍板，因为直接决定第二阶段的工作量。

## 七、事实分层差异（V2.0 §八）

### 7.1 现有能力（这块做得扎实，不要动）

```python
# evidence.py:32-43
OFFICIAL_CONFIRMED            = "OFFICIAL_CONFIRMED"
MULTIPLE_INDEPENDENT_SOURCES  = "MULTIPLE_INDEPENDENT_SOURCES"
SINGLE_SOURCE                 = "SINGLE_SOURCE"
UNVERIFIED                    = "UNVERIFIED"
```

**关键设计**：模型自报的证据字段在入口处被 `pop` 掉（`bot.py:1336-1341`），最终状态由 `evidence.py` 按真实 grounding + 抓取记录重算。**这是整个系统最可信的部分，V2.0 绝不能破坏它。**

### 7.2 V2.0 要的四级标记与现有映射

| V2.0 | 现有对应 | 差距 |
|---|---|---|
| `FACT` | `OFFICIAL_CONFIRMED` + `MULTIPLE_INDEPENDENT_SOURCES` | ✅ 可直接映射 |
| `REPORTED` | `SINGLE_SOURCE` | ✅ 可直接映射 |
| `INFERENCE` | **无** | ❌ 需要新增：模型的分析推断，必须逐句标注 |
| `SPECULATION` | **无** | ❌ 需要新增：无充分证据的猜测，**应默认禁止出现在正文** |

### 7.3 核心矛盾

现有 `evidence_status` 是**事件级**（一条新闻一个状态）。
V2.0 要求**句子级**（同一篇稿子里，「已确认」和「我的判断是」必须分开标）。

**这不是加个字段能解决的**，需要：
- 三稿正文按句/段输出结构化结构（不是一坨字符串），每段带 `basis: FACT|REPORTED|INFERENCE`；
- 或者程序侧按句式识别（`据报道` / `据悉` / `可能` / `尚待确认`）做后处理标注。

我倾向前者（结构化输出），因为后者靠正则识别中文推断句，误判率会很高。

## 八、三个硬约束（必须先解决，否则第二阶段做不出来）

### 8.1 输出 token 上限（**会直接卡死**）

**实测基线**（`state.json` → `ai_stats`）：

```
calls = 217        input_tokens = 1,273,603     output_tokens = 139,827
平均每次输出 = 139,827 / 217 ≈ 644 tokens
```

**V2.0 单条需要的输出量（估算，E 级）：**

| 内容 | 字数 |
|---|---|
| 三稿正文（600–900 字 × 3） | 1800–2700 |
| 三稿标题（3 × 18） | 54 |
| 三稿互动问题（3 × 30） | 90 |
| 9 个标题备选（9 × 17） | 153 |
| 封面三行标题 | 40 |
| 豆包完整提示词 | 700–1000 |
| 无文字背景图提示词 | 400–600 |
| 话题标签 | 60 |
| 事实风险提示 | 150 |
| 质量评分（7 项） | 120 |
| 推荐角度 + 理由 | 50 |
| 主题 + 事实状态 | 60 |
| **合计** | **≈ 3700–5100 字** |
| 加 JSON 键名与结构开销 | **≈ 4300–5800 字** |

**现有上限**：`AI_MAX_TOKENS_ANALYZE = 2200`（`ai_provider.py:170`）

**结论**：即使按中文 1 字 ≈ 0.7 token 的乐观估计，也需要 **3000–4000 tokens**；按 1 字 = 1 token 则需 4300–5800。**2200 一定不够。**

失败路径（已确认的代码行为）：

```
输出被截断 → JSON 不完整 → 解析失败
  → PARSE_ERROR → MODEL_INVALID_RESPONSE
  → _call_model 返回 (None, error)
  → 整条新闻被丢弃（不是降级，是丢弃）
```

**这是「一上线就全挂」级别的阻塞，不是优化项。**

### 8.2 Telegram 4000 字符

| 项 | 值 |
|---|---|
| 单条上限 | 4000（`bot.py:375`） |
| V2.0 卡片估算 | 4000–5500 字符 |
| 结果 | 切成 2 段 |

**真正的问题不是「会切」，而是「切在哪」。**

`_split_html`（`bot.py:243-273`）逐行聚合，只有单行超长才走行内硬切：

```python
for line in text.split("\n"):
    ...
    while len(line) > limit:      # ← 单行超长才进这里
        cut = limit
        ...
```

小红书正文**通常是连续长段落**（一段 200–400 字不分行）。三稿拼在一起如果不用 `\n` 分隔，就会触发行内硬切 → **断在半句话上**，读者看到的是「……哈兰德父亲终于回」+ 下一段「应，曼城真正的危机是」。

**已验证的部分**：分块能力本身有测试（`tests/test_delivery_v12.py:421`），但夹具 `long_card()` 是 40 段 × 150 字、每段都有 `\n`，**从来没测过「单行长文本」这条路径**。

**解法**：V2.0 渲染时强制每稿按段落输出多行，让分块发生在段落边界；并在每块开头加「（1/2）」标记。

### 8.3 测试夹具失真

6 个测试文件用的 `draft_a` 是 20 字的占位串：

```python
# tests/test_pipeline.py:47
"draft_a": "你站哪一边？这次红牌到底冤不冤？",
```

真实生产的三稿是 300–500 字。**测试从来没跑过真实长度的内容**，所以：
- 分块路径在真实卡片上没被验证过；
- 卡片组装的转义/换行在长文本下的表现未知。

涉及文件：`test_pipeline.py` / `test_ai_integration.py` / `test_batch4_v12.py` / `test_batch5_v12.py` / `test_delivery_v12.py`（+ 间接影响的 `test_schema.py`）。

## 九、建议的第二阶段架构

### 9.1 从「一次调用」拆成「三次调用」

现在的结构是「一次调用出 16 个字段」。V2.0 的产出量是现在的 6 倍，**必须拆**：

```
第 1 次  analyze_news（保留现有，微调）
         输入：RSS 素材
         输出：has_valid_news / var_rating / var_reason / event_title /
               fact_summary / evidence_url / source_claims
               + fact_status（FACT|REPORTED|INFERENCE）
               + recommended_angle（A|B|C）+ angle_reason
         预算：2200 tokens（够，不变）

第 2 次  generate_content（已有任务名，但从未被这样用）
         输入：第 1 次的结论 + 证据状态 + 素材摘要
         输出：draft_a/b/c 各含 {title, body, question}，正文按段落数组
               + titles[9]（含 type: 悬念|冲突|信息差）
               + tags[5-8]
               + risk_notes
         预算：需 2600–3200 tokens（当前 `generate_content` = 900，不够）

第 3 次  generate_cover（新增任务）
         输入：事件 + 三行标题
         输出：cover_title / cover_subtitle / cover_footer
               + doubao_bg_prompt（无文字，主用）
               + doubao_full_prompt（带文字，备用）
               + overlay_spec（后期叠加坐标/字号/颜色/描边）
               + aspect_34 / aspect_169
         预算：1800–2200 tokens
```

**为什么拆三次而不是抬高上限**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 抬高上限到 6000 | 改动最小（1 行） | 单次失败全丢；长输出更容易截断；prompt 越长越容易跑偏结构 |
| **拆三次** | 单次失败可局部降级；每步 prompt 短、结构稳定；可独立重试 | 调用次数 ×3，成本 ×2.5 左右 |

**我的判断：拆三次。** 因为「一次出 12 个区块」的 prompt 对模型的指令遵循能力要求太高，实测中这种长结构 JSON 的字段遗漏率会明显上升——而字段遗漏会触发 `validate_scan` 直接拒稿，等于白跑一次还丢新闻。

### 9.2 新增任务的最小改动面（已验证可行）

`AIRouter` 是显式方法分发（`ai_provider.py:790-800`）：

```python
def analyze_news(self, prompt, **kw):    return self._call("analyze_news", prompt, **kw)
def generate_summary(self, prompt, **kw): return self._call("generate_summary", prompt, **kw)
def generate_content(self, prompt, **kw): return self._call("generate_content", prompt, **kw)
```

加一个 `generate_cover` **只需要 2 处改动**：
1. `ai_provider.py:169-174` 加一行 `"generate_cover": _env_int("AI_MAX_TOKENS_COVER", 2200)`
2. `ai_provider.py:790+` 加一个 3 行 wrapper

**不需要动 provider 层、不需要动熔断、不需要动统计。** 这一层设计得很干净。

### 9.3 兼容与回滚

V2.0 §十一 要求「新旧模板可配置切换」。建议：

```python
# focus_config.py 或新增 content_config.py
CONTENT_PACK_VERSION = os.environ.get("CONTENT_PACK", "v1")  # v1 | v2
```

- `v1`：走现有单次调用，字段不变，卡片不变 → **完全等价于今天的行为**。
- `v2`：走三次调用，新字段，新卡片。
- 出问题改环境变量即可回滚，**不用回滚代码**。

### 10.4 三稿「角度差异」的程序侧检测（V2.0 §十一 第三阶段要求）

任务书要求「检查三稿是否真正具有不同叙事角度」。纯靠人眼不行，建议程序侧做三个廉价检测：

```python
def angles_differ(a, b, c):
    # 1) 字符级相似度：三稿两两 Jaccard < 0.55
    # 2) 首句必须不同：a/b/c 的第一句互不包含
    # 3) 结构标记：三稿各自必须含自己的必备段落关键词
    #    A: 出现「双方/一边/另一边」类对立表述
    #    B: 出现「已确认/未确认/证据」类分层表述
    #    C: 出现「影响/后果/接下来」类链条表述
```

不满足就打回重生成一次，仍不满足则降级为「只发 A 稿」并记日志。

## 十一、待你确认的 6 个决策点

1. **封面走哪条路线？** 我建议**默认「无文字背景图 + 后期叠加」**（豆包渲染中文长句不可靠）。若要赌「带文字直出」，出错率会很高。这直接决定第二阶段工作量。

2. **是否接受拆成三次模型调用？** 成本约 ×2.5，但换来「单步失败可局部降级」。若不接受，就只能把三稿正文压到 300 字、提示词压到 400 字，**质量会明显下降**。

3. **新字段是否全部设为可选？** 我强烈建议是。否则 6 个测试文件、630 个用例会大面积失败，且生产上会出现「字段缺一个就整条不发」。

4. **`INFERENCE` 是否允许出现在正文？** V2.0 §八 允许，但要求标注。我建议**允许在 C 稿的「潜在影响」段落出现，且必须带「可能/取决于/尚待确认」措辞**，其余位置禁止。

5. **扫描模式是否补 `tags` 字段？** 现在只有早报有。V2.0 §九 要求每条新闻都有 5–8 个标签，扫描模式属于「每条新闻」，应该补。

6. **质量评分（§十）是否真的要落库？** 现在全仓库没有评分机制。若只做「内部编辑评估」，建议**不落 state.json**（避免膨胀），只在卡片末尾显示一行总分 + 硬门槛结论。
